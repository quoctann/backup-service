# Disaster recovery checklist

1. **Contain the incident.** Stop application writes if necessary and suspend scheduled backups if they might overwrite/prune needed history. GitOps can undo a manual suspension; update desired state. Suspension does not cancel an active Job. Preserve logs and the original disk, and avoid repeatedly stressing failing hardware.
2. **Identify what survived.** Inventory the disk/off-site copies, source versions, completed-set metadata, configuration, extension requirements, and credentials in your independent secret store. A backup on the same failed host is not a disaster-recovery strategy. Never initialize a new marker over an unidentified disk.
3. **Recover infrastructure safely.** Rebuild the host/k3s as needed; mount the existing filesystem by its recorded UUID without formatting. Verify UUID and mountpoint before exposing `/mnt/backup-hdd/postgres`. Restore UID/GID access carefully. Reestablish namespace, DNS, image registry access, isolated PostgreSQL/PVC, and version-matched extension packages. A recovered disk can initially be mounted read-only.
4. **Select a recovery point.** Verify a known successful set and all manifest checksums. If corrupt or incomplete, try an earlier independent copy. Document the data-loss interval: daily logical snapshots do not offer point-in-time recovery or zero data loss. Separate databases/targets do not share an atomic snapshot; reconcile cross-database business state.
5. **Restore in isolation.** Follow [the restore runbook](restore.md): matched tools, reviewed globals without role passwords, preserved database metadata, stop-on-error, and application-level verification. Recover login passwords through the secret system; they should not be present in globals backups.
6. **Approve cutover.** Keep old production and the backup immutable where possible. Coordinate credentials, Service endpoints, application connection pools, and a maintenance window. Confirm that only one writable production instance is reachable; retain a rollback plan. Never blindly change live Service selectors while writes continue.
7. **Resume protection.** After recovery, take a new backup, verify an independent copy, and complete another restore drill. Re-enable scheduling intentionally, clear temporary credentials/Pods, review alerts, and record the actual recovery point/time and gaps.

Keep an offline recovery inventory: filesystem UUID and disk identity, registry/image digests, supported PostgreSQL versions, backup schedule/retention, workload repository path, secret-store recovery instructions, and restore-test results. Do not put passwords into this inventory unless it is an appropriately encrypted secret store.
